# 優先タスクを最小作業単位の指示書にする

正本はAGENTS.md、docs/AGENT-WORKFLOW.md、tickets。作業回の開始・終了と証跡の規則は `.agents/skills/repository-task-closeout/SKILL.md` に従う。この指示書は案内であり、状態を二重管理しない。単位の完了は作業ログとチケットに書き、文書には印を付けない。

先例は docs/CLAUDE-REPAIR-INSTRUCTIONS.md（T100）、docs/HUMAN-BLOCKERS.md（T105）、docs/CLAUDE-IMPLEMENTATION-BATCH.md（T109）、docs/PRIORITY-WORK-UNITS.md（T120）。T113（docs/PRIORITY-TASKS-2026-10-11.md）では、1チケットを1つの塊として書いたこと、実装の存在を確かめずに完了確認を書いたこと（未実装の `.env` 読込み、存在しない `src/connectors/`）が補完の理由になった。

## 1. 対象を機械的に集める
1. `./scripts/run src/cli.ts tickets` の出力を証跡に保存する。対象（例: P0/P1で状態がdone以外）を `grep` で抜き出し、別ファイルに保存する。対象から漏れていても、対象を止めている下位優先度のチケット（依存の先）は加える。
2. 各チケットの本文とdependsの先、人の回答（docs/HUMAN-TASKS.md、docs/HUMAN-BLOCKERS.md、最新の比較・結果文書）を読む。最新の本人回答を古い「未回答」の記録より優先する。
3. doneになっていても、直近に別のエージェントが閉じたものは受け入れ条件と照らす。食い違いは「確認が必要なもの」として事実と証跡で書き、他者のチケットや終了済みログは書き換えない。

## 2. 単位に分ける
- 1単位は1回の作業（目安15〜90分）で終わり、成果物と完了確認を1つずつ持つ。1チケットを1単位にまとめない。
- 欄は、ID（`<チケット番号>-<連番>`）、担当、内容、前提、完了確認、外部区分（なし / 判断 / 外部操作 / 課金 / 投稿）。人の単位には目安の時間も入れる。
- 人の単位は、判断（決めて回答するだけ）と、承認後の外部操作・課金を別の単位にする。判断の単位を先に並べる。秘密値は求めず、「保管済み」「金額」「名前」だけを報告してもらう。予算の希望額は承認として扱わない。
- agentの単位は「今すぐ着手できる」「人を待つ間に模擬で先行できる」「人の承認後の実試験」に分ける。依存が未完了のチケットの先行分は、新チケットの案として示す（勝手に作らない）。
- 不具合の修正は、回帰試験の追加と修正前の失敗の確認を、別の単位として先に置く。
- 依存の矛盾（例: 方針では任意の工程が、親チケットの必須依存になっている）は、見直しの単位として案を出す。

## 3. 書いた事実を確かめる
- 完了確認に書くコマンド・ファイル・関数・設定は、実在をリポジトリで確かめる。未実装なら「未実装」と書き、確認方法を作る単位を別に置く。
- 他者の成果について書くこと（ファイルの欠落、試験件数、実行の失敗）は、今回の作業回で再実行して証跡を残す。以前の結果を読み替えない。
- 文書の一覧が対象と一致するかを機械的に照合する。対象のIDがすべて一覧表の行にあり、余分な行は意図したものだけにする。あわせて、本文中のパスの存在と、表の列数・空欄を検査する。出力と終了コードを `evidence/doc-verify.txt` などに保存する。

## 4. 例外と終了
- 同じ作業ツリーで別のエージェントが動いている兆し（未終了の作業回、数分以内の更新）があれば、書き込みを止めて利用者に知らせる。
- 既存の整理文書に誤りがある場合は、本文を書き換えず、冒頭に作業回つきの追記と新文書への案内を置く。
- 新チケット案の作成、依存の変更、契約・課金・投稿は、利用者の了承を得てから別の作業回で行う。
