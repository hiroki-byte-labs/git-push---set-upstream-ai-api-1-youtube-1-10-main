# 課題を確かめ、チケットに切り出して改善する

正本はリポジトリの `AGENTS.md`、`README.md`、`docs/SPEC.md`、`docs/STATUS.md`、`docs/AGENT-WORKFLOW.md` とtickets。以下のパスはリポジトリルート基準。別の管理方式のリポジトリへticketsやworklogの仕組みを導入しない。

## 依頼の範囲を決める

会話全体で既に許可された範囲を引き継ぎ、通常の可逆的な実装・ローカル検証のたびに確認を求めない。今回の依頼と既存の許可を、次のように使い分ける。

| 依頼 | 進める範囲 |
|---|---|
| 状況確認・課題列挙 | 調査、再現、候補と優先順の提示まで。実装修正はしない |
| チケット化 | 調査とローカルticketsへの登録まで。明示された範囲を登録し、実装は別の許可に従う |
| 改善・既存作業を進める | 許可範囲の既存チケットを実装・検証。新たに見つかった範囲外の課題は切出し案を残す |
| 課題をチケット化して改善・改善サイクルを回す | 指定範囲の調査、必要なローカルチケットの作成、実装、検証、残件再確認まで進める |

このSkillで実行するのは依頼に含まれたローカル作業だけ。契約・API課金・課金デプロイ・push・投稿・本人の採用/承認は既存の規約に従う。既存の許可がない外部Issue投稿も行わない。本人の考察や承認を試験データで代行しない。

## 1. 現状と証拠を集める

- 開始時の必読文書、対象チケットと直接依存を読み、`./scripts/run src/cli.ts check` と `next`、必要なら `tickets` とGit差分を確認する。既存の作業ログ運用に従って自分の作業回を開始する。他者のopen作業を閉じて先へ進まない。
- `next` はreadyだけを表示する。依存完了backlog、reviewの技術的残件、done成果の不具合、足りない受入証跡、前回の残件も照合する。エンジン未起動などは、導入/起動可否の調査と本人の音色採用判断を分ける。
- 「実装済み」「テスト済み」「実環境で検証済み」「本人承認済み」を分ける。古いログの失敗も成功も、現在の事実と取り違えない。疑わしい点は該当コードと最小の再現で確かめ、未確認なら仮説と書く。
- 調査対象は依頼された機能・既知の不具合・受入条件に絞る。課題を増やすために無関係な改善や一般的な好みを起票しない。

## 2. 実行できる単位へ切り出す

分解には `.agents/skills/task-work-units/SKILL.md` を使う。最低限、次の対応を残す。

| 項目 | 記録する内容 |
|---|---|
| 課題と根拠 | 利用者への影響、再現手順/証拠、確認済みか仮説か |
| 既存チケット | 同じ目的・原因・受入条件のチケット、依存と現在状態 |
| 作業と完了条件 | 1回で実装・検証できる成果、対象外、必要試験 |
| 担当と前提 | agent/human、今できる作業、技術依存、本人判断/外部承認 |

既存チケットの範囲内なら、そのチケットの新しい作業回で補修する。doneでも不具合を放置せず再開できるが、過去の結果や閉じたログは残し、追加修正として記録する。独立した目的・受入条件なら新規へ分ける。単に古い整理文書に残っているだけで重複起票しない。

新規登録が許可されていれば `tickets/templates/TICKET.md` に従う。最新番号と既存の内容を再確認し、上書きしない方法で作成する。owner/status/priority/milestone/depends、実施範囲/対象外、受入条件/検証方法を埋める。依存を外して着手可能に見せない。登録が許可範囲外なら同じ内容の切出し案を残す。チケット化を既に依頼されている場合は、再度確認して止めない。

## 3. 優先して1件ずつ改善する

ユーザー指定を優先し、指定がなければ、成果の欠落・誤承認・既存成果物への誤書込みなどの不具合、後続を止める検証不足、独立した機能改善の順で選ぶ。重大度と依存によって調整し、固定件数で打ち切らない。

- 原則1チケット・1作業回で実装・検証・記録する。別チケットへ移る前に現在の作業回を閉じる。調査中の作業回があれば、二重startせず正本の順序を守る。
- 不具合は可能なら先に回帰試験を加え、修正前の失敗を保存してから直す。機械的な文言一致だけの試験や、低影響の文書修正のための不要な試験は追加しない。
- 受入条件に必要な対象試験と型検査を実行する。共有経路を変えたら適切な統合/全体試験も行う。未測定・欠落した検査を成功扱いしない。注入transport・合成素材・実サービス・実再生の結果を区別する。
- 分担を許可された複数工程の作業は `.agents/skills/model-router/SKILL.md` に従い、独立して確認できる実装・調査・レビューを `agentctl run` へ渡す。親は指示・統合・最終検証を担当する。推薦を見るだけで全工程を親が実施した状態を分担済みとしない。切出しが不適切な単発作業は親で実施し理由を残す。
- 生成経路の検証は既存outputsを保護し、`.agents/skills/sample-render-verification/SKILL.md` を使う。分野別のSkillがあれば該当工程で読む。モデル・製品の選択と子の計測はModel Routerとagentctlの正本に従う。
- `.agents/skills/repository-task-closeout/SKILL.md` に従ってチケット/STATUS/証跡/WORKLOGを揃え、finishとcheckを成功させる。使用量はToken Monitorで確認し、未計測を計測完了と報告しない。

## 4. 残件を再確認して続ける

1件の完了後に、最新のチケット・依存・今回見つかった問題を見直す。許可された範囲に独立して進められる作業が残るなら、次のチケットで続ける。新しい問題で元の修正が未完了と分かった場合は、その受入条件を先に満たす。

次のいずれかで区切る。

- 依頼された範囲の実装と必要検証が完了した。
- 残る作業には具体的な本人判断/外部承認/環境条件/他者の作業が必要で、独立して進められる項目も尽きた。
- ユーザーが停止・範囲変更を指示した、または明示された予算/実行枠に達した。

「readyなし」や数件の成功だけでは課題なしと結論しない。一方、新しい仮説を無限に増やして終わらない探索にしない。同じ障害の変化のない再試行は繰り返さず、証拠・必要条件・再開手順を残す。監視/定期実行は頼まれた場合だけ設定する。

報告は今回の完了、検証の範囲、残るagent作業、本人に必要な作業を短く分ける。「未検証」と「人待ち」を混同せず、全体の品質合格や課題枯渇を証拠以上に断定しない。

## 呼出し例

- `改善サイクルを回して。音声と承認の課題を調べ、必要なチケットを切って、ローカルで進められる修正と検証まで行って。`
- `まだエージェントが進められる課題がないか、このSkillで調べて。今回は候補一覧まで。`

このSkill自体の作成・更新だけを依頼された場合は、上記の課題探索やチケット起票・実装の開始許可とは解釈しない。試用は読み取り調査や一時領域の模擬ケースに限定し、実施した範囲を記録する。
